# 编码规范

## 1. 通用要求

- 优先清晰、可维护和可测试，不以减少行数为目标。
- 类型、函数和模块命名应表达职责；避免缩写堆叠和含糊的 Manager/Helper。
- 不新增无必要的全局可变状态。
- 不吞掉异常；错误必须被转换为调用方可理解的结果或明确传播。
- 不在日志中输出令牌、密码、签名材料、私有文件内容或个人数据。
- 注释解释原因、约束和不明显的决策，不重复代码本身。
- 公共 API 必须记录参数约束、线程要求、错误语义和兼容性。

## 2. Kotlin

- 使用不可变数据优先；状态变更通过明确的方法或 reducer。
- 避免暴露可变集合；对外返回只读接口或快照。
- 使用结构化并发；禁止随意创建脱离调用者生命周期/所有权的 GlobalScope 任务。
- I/O、解析、进程等待和 CPU 密集任务不得运行在主线程。
- Flow/Channel 的缓冲、重放、背压和关闭行为必须明确。
- API 中明确区分 nullable、空值、失败和未加载状态。
- 公开类与函数应保持最小可见性，内部实现使用 internal/private。
- 扩展函数不得隐藏重要副作用。

## 3. Compose

- Composable 主要负责 UI 描述，不承载复杂业务逻辑。
- 遵循状态向下、事件向上的单向数据流。
- 使用稳定参数和不可变 UI state，避免不必要重组。
- 副作用使用对应 Compose effect API，并明确 key 与清理逻辑。
- 不在 Composable body 中直接启动无约束后台任务。
- 事件回调应表达用户意图，不直接暴露底层数据库/网络实现。
- 提供语义标签、触控目标、键盘/焦点行为和适当的无障碍支持。
- 主题值统一来自 Design System，避免页面硬编码颜色和间距。
- 不为追求“零生命周期”而误删必要的 Android 生命周期管理；目标是 UI 不依赖传统 View 生命周期与 View 树。

## 4. Java

- 遵循 Google Java Style，使用明确的访问修饰符和不可变字段。
- 对资源使用 try-with-resources 或等效可靠释放机制。
- 避免阻塞主线程和不受控线程池。
- 公共方法定义异常契约和空值语义。

## 5. C/C++ 与 JNI

- 头文件声明稳定接口，内部实现尽量隐藏。
- 明确指针所有权；优先 RAII、智能指针和作用域资源管理。
- JNI 边界检查参数、异常和数组/字符串访问释放。
- 不跨 JNI 保存局部引用；全局引用必须有配对释放路径。
- 避免在持有锁时调用 Java 回调或执行长时间 I/O。
- 对 Native buffer、AST、解析树和缓存定义容量策略与内存预算。
- 大文件路径应采用增量/分块处理，避免不必要的全量复制。
- 性能优化必须附带基准输入和测量结果。

## 6. Rust（适用时）

- 优先利用所有权和借用系统表达资源边界。
- FFI 类型必须明确布局、生命周期和错误映射。
- 不将 panic 穿越 FFI 边界。
- unsafe 代码必须缩小范围并说明安全不变量。

## 7. Gradle

- 依赖版本优先使用 Version Catalog。
- 通用配置放入 convention plugin/build-logic，不复制粘贴到每个模块。
- 模块脚本只保留模块特有配置。
- 依赖变更需说明来源、许可证和是否引入重复类/资源。
- 避免动态版本和不可复现依赖。

## 8. 命名与格式

遵守项目现有 formatter 和目录惯例；若模块存在历史风格，新增代码应逐步向统一规范靠拢，不应在无关变更中批量重排全仓库。
