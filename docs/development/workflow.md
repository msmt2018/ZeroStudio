# 开发与交付流程

## 1. 开发前

1. 确认目标功能所属模块和公开 API。
2. 阅读模块现有实现与相关 ADR。
3. 确认是否引入外部源码、SDK、Native 库或许可证义务。
4. 将复杂任务拆分为可独立审查和验证的阶段。
5. 对架构变更先更新 ADR 或模块地图。

## 2. 实施顺序

推荐按依赖从底向上开发：

1. 领域模型、接口和数据契约。
2. 基础设施适配与 Native/JNI 实现。
3. 应用层用例、状态和事件。
4. UI 组件、导航和页面。
5. 单元、集成、仪器和性能测试。
6. 文档与变更记录。

不要先实现临时页面，再反向创建底层 API。

## 3. 分支与提交

- 功能分支命名建议：`feature/<topic>`、`fix/<topic>`、`docs/<topic>`、`refactor/<topic>`。
- 提交应聚焦单一逻辑变更，避免将无关格式化与功能修改混合。
- 提交说明应指出领域/模块和动作，例如 `editor: improve incremental parse scheduling`。
- 不在提交中包含密钥、签名文件、用户数据或本地构建产物。
- 遵守仓库分支保护、签名和 PR 要求；实际策略以 GitHub 仓库设置为准。

## 4. 代码审查

PR 描述至少包括：

- 背景与问题。
- 设计方案及替代方案。
- 受影响模块与 API。
- 兼容性、数据迁移和许可证影响。
- 测试命令及结果。
- CI 运行链接。
- UI 截图或录屏（仅 UI 变更时）。
- 未完成事项与已知风险。

审查重点：依赖方向、线程/资源安全、错误处理、性能、可访问性、测试可重复性和文档同步。

## 5. 构建配置

中央 Android 配置位于 build-logic 的 BuildConfig 和 Android module convention 配置。新增 Android Library/Application 应优先接入统一配置，不得自行覆盖 compileSdk、minSdk、targetSdk、ndkVersion，除非存在已记录的兼容性原因。

独立 composite build 必须单独验证插件解析与配置，不能假设主工程成功就代表独立构建成功。

## 6. CI 与构建验证

建议验证顺序：

1. Gradle Wrapper 与配置阶段。
2. 受影响模块编译。
3. 相关单元测试。
4. Native/CMake 编译（若涉及）。
5. 主 Application APK 构建。
6. 仪器测试/模拟器冒烟测试（适用时）。
7. 真机安装与核心流程验证（涉及平台行为时）。

网络依赖下载失败与源码编译失败应区分。HTTP 429、DNS、仓库不可用等基础设施错误，应记录为依赖解析问题，不应误报为代码编译错误。

## 7. 发布流程

- 发布版本、版本代码和 Git 提交必须可追踪。
- Release 产物应关联源码 commit、构建工作流和构建参数。
- 多 ABI APK 应清楚标注 ABI 与签名状态。
- 发布前验证安装、启动、升级路径和核心开发流程。
- 不将“上传成功”视为“运行验证成功”。

## 8. 完成定义（Definition of Done）

任务只有在适用项均完成后才可关闭：

- [ ] 实现符合架构与模块边界。
- [ ] API/行为有文档或注释。
- [ ] 错误、取消和资源释放路径完整。
- [ ] 相关测试通过。
- [ ] 相关 Gradle/Native 构建通过。
- [ ] CI 结果已核对。
- [ ] 必要时完成模拟器/真机验证。
- [ ] 文档、模块地图和 ADR 已同步。
- [ ] 已知限制与未验证范围明确记录。
